# Camera capture

**Purpose:** The core capture pipeline for `feature:camera` — an Android take on iOS's (Not Boring) Camera app. Skeuomorphic viewfinder UI (levers, dials) driving a raw Camera2-backed capture flow.

**Current state:**
- Raw `android.hardware.camera2` (`CameraManager`/`CameraDevice`/`CameraCaptureSession`/`ImageReader`) in `CameraController` (`data/`) — **not** CameraX. One capture session with two independent `ImageReader` surfaces: a `YUV_420_888` preview reader (fast repeating request, plain auto-exposure by default) and a JPEG reader for stills (one-off `capture()` per photo). The two share no session-wide state, so a long manual exposure never blocks or degrades the live preview. The live preview is *rendered*, not just captured — `CameraController` never targets the repeating request at a caller-supplied `Surface` at all; `ui/CameraScreen`'s `CameraPreviewRenderer` (`ui/gl/`) draws each delivered frame onto the on-screen `TextureView` itself via app-owned GLES (see this file's own key-decisions entry for why).
- Lens switching (`LensSnapshot`, from `shared:diagnostics`, via `OutputConfiguration.setPhysicalCameraId`), flash mode (`FlashMode`, applied per still-capture request).
- **Auto mode** (default): the deck shows a single `ExposureDial` controlling real AE exposure compensation (`CONTROL_AE_EXPOSURE_COMPENSATION`) — a +/- EV bias applied on top of full auto-metering (`CONTROL_AE_MODE_ON`); auto-exposure still freely picks ISO/shutter, the dial only biases what it converges toward. Displayed as signed EV to one decimal (e.g. "+1.0"). Gated independently of `MANUAL_SENSOR` via `shared:diagnostics`'s `AeCompensationCapability` (`CONTROL_AE_COMPENSATION_RANGE`/`STEP`, `null` when range is `[0,0]`) — unlike manual ISO/shutter this works on nearly every device. EV index resets (not re-clamped) to the lens's 0 EV stop on lens switch, since the range differs per lens.
- **Manual mode**: `IsoDial` + `ShutterSpeedDial`, two independent always-visible dials, gated on `CameraCharacteristics` `MANUAL_SENSOR` capability (`manualIsoSupported` in `CameraUiState`) — hidden/disabled on devices that don't report it. `CONTROL_AE_MODE_OFF` still fixes ISO and shutter together; there's no "ISO manual, shutter auto" mode.
- Mode switching is exclusively via tapping `ModeLever` (`CameraViewModel.onManualModeToggled()`); dragging a dial has no manual-mode side effect. Auto-exposure's ISO/shutter/EV are tracked live off the preview's capture results the whole time auto mode is active, so switching to manual continues from whatever auto had converged on — no explicit sync code needed.
- Auto <-> manual visually plays a mechanical seal/unseal transition on `DialWheel` (barrel sinks with a hard-stop bounce, shutter panels slide in painted with the deck's exact gradient, ISO/SHUTTER staggered ~30ms apart) rather than the earlier plain `Crossfade` — see issue #19.
- Manual ISO/shutter ladders (`isoStops`/`shutterStops`) are the standard stop ladder filtered to the selected lens's actual supported range, not a fixed list; AE compensation's ladder (`aeCompensationSteps`) is just the hardware's own integer step range, no curated list.
- Live preview reflects manual ISO/shutter while dragging the dial, capped at a safe exposure-time ceiling (`PreviewMaxExposureTimeNs`, brightness compensated via ISO) so it never drops frame rate; the actual capture always uses the real, uncapped selected values.
- Viewfinder grid overlay, off by default.
- **Horizon-level indicator** (issue #31, redesigned in #41): a single hairline in `HorizonLineOverlay` broken into three thirds — static outer left/right thirds that never move, and a dynamic center third tracking live device roll. The center third's span matches `ViewfinderGridOverlay`'s own center-column math (`extent/3`..`extent*2/3`, computed independently of grid visibility) so it lines up inside the grid when shown. Drawing axis (width-thirds vs height-thirds) is picked directly from `DeviceOrientationState.quadrant` rather than rotating a fixed layout, so the statics land on the grid's fixed divider positions in every orientation; only the small residual-from-level angle rotates the center segment. All three segments share one base stroke/alpha; when residual roll crosses under a hysteresis-guarded threshold the whole line briefly flashes brighter and fires one haptic tick. `StrokeCap.Butt` (not `Round`) avoids bright seam artifacts between segments.
- **Zebra-stripe clipping overlay** (`ZebraOverlay`, issue #6): rides the same preview `ImageReader` frames the renderer already receives — `CameraController`'s `previewImageAvailableListener` classifies each frame's luma plane directly (`ZebraMask.fromLumaPlane`, throttled to one classification per ~66ms), only while `CameraController.setZebraAnalysisEnabled(true)` — driven by `DialWheel.onDragActiveChanged` on the ISO/shutter/EV dials, wired in `ExposureOrManualDials`. No separate capture mechanism (no `PixelCopy`, no dedicated stream) — frames are already flowing continuously as a side effect of the preview repeating request, classification just piggybacks on them when enabled. `ZebraMask.fromLumaPlane` (pure domain function) buckets the luma plane into a 24x32 grid by majority vote per cell, sampling a bounded number of pixels per cell rather than every pixel (keeps cost independent of the source frame's resolution — see its own doc); `CameraController.zebraMask` is exposed as its own `StateFlow<ZebraMask?>` (not folded into `CameraUiState`, same reasoning as `CameraViewModel.zebraMask`) since it can emit at up to ~15fps while dragging. An `ImageReader` buffer is always in the sensor's native (landscape) orientation regardless of display orientation, so `ZebraMask.rotatedBy`/`CameraController.analysisRotationDegrees` (from `CameraCharacteristics.SENSOR_ORIENTATION`) still apply.
- **Manual focus: tap-to-focus + hold-to-position ring + dedicated FocusDial** (issue #21, reworked after initial ship — see this section's own history): a plain tap sets the AF metering region at the tap point (`CameraController.triggerAutoFocus`) and pushes a one-off `CONTROL_AF_TRIGGER_START` capture in `CONTROL_AF_MODE_AUTO` — **not** `CONTINUOUS_PICTURE` — see this file's own key-decisions entry below for why `AUTO` is required for a real lens movement on this hardware. The *repeating* request also stays in `AUTO` (`CameraController.pendingAfModeAuto`) until `previewCaptureCallback` observes the triggered scan actually settle (`FOCUSED_LOCKED`/`NOT_FOCUSED_LOCKED`), at which point it reverts to `CONTROL_AF_MODE_CONTINUOUS_PICTURE` to resume tracking, bounded by a 2s fallback in case a HAL never reports a settled state. A tap also drives its own visual feedback: `FocusTapIndicator` (bracket-cornered AF box, `ui/component/`) appears at the tap point and fades once `CameraController.afConvergenceState` (mapped from `CaptureResult.CONTROL_AF_STATE` into `AfConvergenceState`) reports the scan has left `SCANNING`, not a fixed guessed timer.
  - A long-press on the viewfinder instead shows a mechanical, gear-toothed `FocusRing` (`ui/component/FocusRing.kt`) at the *actual touch point*, with a magnified ("loupe") crop of the live preview centered there — but, per the UX rework, **the viewfinder's own long-press no longer adjusts focus at all**, it only positions the ring/loupe. `TextureView.getBitmap()` snapshots exactly what `CameraPreviewRenderer`'s GLES pipeline is currently drawing (no separate capture path), cropped+refreshed on a throttled loop (~80ms, crop radius scaled to the ring's own ~92%-of-viewfinder size so magnification doesn't turn to mush) while the hold is active. A loupe-local (never full-viewfinder — an explicit non-goal) focus-assist highlight outlines locally sharp edges within the crop, computed by the pure `FocusPeakingMask.fromLuma` (a cheap gradient-magnitude proxy over the crop's own luma, coarse-gridded like `ZebraMask`) and drawn clipped to the loupe's own circle.
  - `FocusDial` (`ui/component/FocusDial.kt`), a new dedicated control in the deck row (visible only when `CameraUiState.manualFocusSupported`), is the *only* thing that actually changes the manual focus distance: touch-down begins tracking immediately (no long-press delay — there's no competing tap gesture on this control), and a continuous vertical drag accumulates rotation radians fed through `manualFocusDistanceForRotation` (domain, ~1.5 full turns sweeps the lens's whole `[0, maxFocusDistanceDiopters]` range, starting from wherever continuous AF had last converged when the *dial's* hold began) — the same function the viewfinder's own rotation gesture used before this rework. Visually it reuses `DialWheel`'s own barrel/well/center-caret drawing primitives (`drawBarrel`/`drawWell`/`drawCenterCarets`, `internal` in `DialWheel.kt` specifically for this reuse) but with its own continuous-drag gesture model, not `DialWheel`'s click-ratchet — there's no discrete value ladder for focus distance. Its value readout is formatted by the pure `formatFocusDistance` (domain) — meters (one decimal) above 1m, centimeters below, `∞` at `0` diopters (optical infinity).
  - The ring now stays visible as long as *either* the viewfinder is long-pressed or `FocusDial` is held (two independent hold signals in `ui/CameraScreen`: `screenHoldPosition`/`dialHeld`), dismissing only once both release. The viewfinder's touch point wins whenever it's held (the more specific signal); holding only `FocusDial` (no screen touch) falls back to centering the ring on the viewfinder, exactly like the ring's own original always-centered behavior. This lets the dial be operated one-handed while the other hand repositions the loupe by touching the viewfinder, or the dial alone while just watching the frame.
  - Releasing **locks** the last dialed focus distance (`CONTROL_AF_MODE_OFF` stays applied to both the live preview and the next still capture) until the next tap (resumes continuous AF) or hold — this "commit" is still just `CameraController.setManualFocusDistance` not being called with a new value again, no separate commit step. Gated per-lens on `CameraCharacteristics.LENS_INFO_MINIMUM_FOCUS_DISTANCE` (`shared:diagnostics`'s `ManualFocusCapability`/`CameraController.manualFocusCapability` — `null`/hidden on a fixed-focus lens, i.e. that characteristic being exactly `0`), independent of `MANUAL_SENSOR` (which only gates ISO/shutter). The tap-point-to-sensor-coordinate mapping (`displayFractionToSensorFraction`) approximates the whole active array as visible in the viewfinder (no center-crop offset) — a deliberate simplification given `CONTROL_AF_REGIONS` is itself a coarse rectangle, not a single-pixel target; confirmed on-device (Pixel 9 Pro) to produce sane, tap-location-varying regions, but not verified against a device with a more significant preview-vs-active-array aspect mismatch.
- Capture writes JPEG bytes straight to `MediaStore` (own encode/write path, no CameraX `ImageCapture` helper); no success toast on capture (removed deliberately, see issue #3).
- **RAW/DNG capture, opt-in via a persisted setting** (issue #45, UI reworked from an initial per-shot toggle after user feedback): `shared:diagnostics`'s `RawCaptureCapability` (per-lens `REQUEST_AVAILABLE_CAPABILITIES_RAW` + a `RAW_SENSOR` output size, mirroring `ManualIsoCapability`/`ManualFocusCapability`'s own nullable-capability pattern) is a live per-lens hardware-support signal (`CameraUiState.rawCaptureSupported`), while `CameraSettings.captureRawByDefault` (`ui/SettingsScreen`'s "RAW CAPTURE" lever, alongside GRID/HISTOGRAM/HORIZON, with a caption carrying the required large-file warning) is the persisted user *preference* — `feature:settings` has no way to know which lens is active, so it can only express intent, not a guarantee. `ui/CameraScreen`'s `capture()` ANDs the two right before calling `takePhoto`, so enabling the setting while on a non-RAW lens silently captures JPEG-only and switching to a RAW-capable lens with the setting already on picks it up automatically, no extra tap. A lens reporting the characteristic alone isn't trusted outright: `CameraController.openCamera` additionally builds a candidate third `RAW_SENSOR` `ImageReader` (`maxImages = 1`) and verifies the 3-surface (preview + JPEG + RAW) session via `CameraDevice.isSessionConfigurationSupported` (API 29+; unavailable below that, so RAW is never attempted pre-Q) before actually including it — any failure of that check falls back to the plain 2-surface session, silently treating RAW as unavailable for that bind rather than risking the whole session's `onConfigureFailed`. A "with RAW" capture issues one still-capture request targeting both the JPEG and RAW surfaces (so both come from the identical sensor frame), then correlates the delivered RAW `Image` with its `TotalCaptureResult` by `SENSOR_TIMESTAMP`/`Image.getTimestamp()` — not by callback arrival order — before handing both to `DngCreator` (off the main thread, alongside the JPEG's own `MediaStore` write) to produce a spec-valid `.dng` saved next to the JPEG. LUT grading never touches the RAW output — only the JPEG companion is graded, exactly as before; a RAW/DNG write failure is swallowed rather than losing the JPEG that already succeeded.
- No manual white balance yet.

**Key decisions:**
- Migrated off CameraX (`Preview`/`ImageCapture` use cases) onto raw Camera2 in issue #10 — CameraX's `Camera2Interop`/`Camera2CameraControl` only exposes session-wide dynamic capture-request overrides, with no supported way to keep a fast repeating preview request independent from a still capture's request. That coupling caused long manual shutter speeds (4s/8s/16s+) to visibly stall the preview and, at the longest speeds, fail capture outright (confirmed via on-device `adb logcat`: queued long-exposure preview frames backed up in the HAL ahead of the actual still request until CameraX's own capture-session watchdog aborted and reset). Managing the `CameraCaptureSession` directly removes the coupling: preview and capture are independent Camera2 requests from the start.
- `CameraController`/`CameraRepositoryImpl` are `@Singleton` (`di/CameraModule`) — without it, `CameraViewModel`'s constructor injection and `ui/CameraScreen`'s separate `EntryPointAccessors` call each resolved their own unscoped instance, so `bindCamera()` ran on one while every other operation (including `takePhoto()`) ran on another that was never bound. Regression from the #8/#9 Clean Architecture refactor, fixed alongside #10.
- Camera2 has no lifecycle-aware bind/unbind like CameraX's `bindToLifecycle` — `CameraController` implements `LifecycleEventObserver` itself, opening the device/session at `ON_START` and closing at `ON_STOP`, plus a separate `unbindCamera()` for the hosting view itself being destroyed. It's the *sole* lifecycle-driven trigger for opening/closing the session — `ui/CameraScreen` never independently reacts to lifecycle events itself (only to `previewSurfaceTexture`/`previewViewSize`/`selectedLens` *state* changes). Keep it that way: an earlier attempt at working around the preview-resolution bug below added a second, UI-owned `LifecycleEventObserver` on the same `Lifecycle` to swap in a fresh `SurfaceTexture` on every `ON_START`; that raced `CameraController`'s own observer for `Surface` identity and crashed (`IllegalArgumentException: Surface was abandoned` inside `createCaptureSession`). Reverted — see git history on this file's own commits for the full incident.
- Manual-mode pending values (`pendingManualIso`, `pendingManualShutterNs`) are cached in `CameraController` so they survive a rebind (e.g. switching lenses mid manual-mode).
- Capability-gated per lens, not per device — `manualIsoSupported`/`AeCompensationCapability` (`shared:diagnostics` types, via `CameraCapabilityChecks.kt`) are evaluated against the *selected* lens's `CameraCharacteristics`, since front/back/tele lenses can differ.
- Lens identity/capability model (`LensSnapshot`, `RawCaptureCapability`/`ManualIsoCapability`/`ManualFocusCapability`/`AeCompensationCapability`) and lens enumeration (`LensEnumerator`) live in `shared:diagnostics`, not this module — a pure type/import relocation off this feature's own now-deleted equivalents, no capture-pipeline behavior change. See `docs/features/camera-diagnostics.md`.
- `DialWheel`'s shutter panels reproduce the deck background by rebuilding `CameraChrome.DeckGradientStops` at a measured position, not a real backdrop-capture — only correct because that deck area is a plain vertical gradient with no horizontal variation or grain (issue #19).
- **Tap-to-focus's one-off trigger request uses `CONTROL_AF_MODE_AUTO`, not `CONTROL_AF_MODE_CONTINUOUS_PICTURE`** (issue #21 follow-up) — confirmed via on-device `CaptureResult.CONTROL_AF_STATE`/`LENS_FOCUS_DISTANCE` logging (Pixel 9 Pro, `caiman_beta`) that issuing `CONTROL_AF_TRIGGER_START` while the request was already `CONTINUOUS_PICTURE` does not force a genuine re-scan toward a newly-set `CONTROL_AF_REGIONS` on this hardware: `CONTROL_AF_STATE` jumped directly from `PASSIVE_FOCUSED` to `FOCUSED_LOCKED` in a single frame with `LENS_FOCUS_DISTANCE` bit-for-bit unchanged — the trigger just locked whatever continuous AF had already passively converged to and silently ignored the new region, so tapping never visibly refocused the lens. `CONTROL_AF_MODE_AUTO` reliably forces a real `ACTIVE_SCAN` on trigger (confirmed on-device: focus distance visibly sweeping across several frames before locking on a genuinely different value). A single `AUTO` frame isn't enough for the scan to complete, so `CameraController.pendingAfModeAuto` keeps the *repeating* request in `AUTO` too until `previewCaptureCallback` observes the scan settle (`FOCUSED_LOCKED`/`NOT_FOCUSED_LOCKED`), then reverts to `CONTINUOUS_PICTURE` to resume tracking — a bounded 2s fallback (`AfAutoModeFallbackTimeoutMs`) guards against a HAL that never reports a settled state at all.
- **`ImageReader.close()` for `imageReader`/`previewImageReader`/`rawImageReader` is posted onto `backgroundHandler` rather than called directly from `CameraController`'s main-thread `controllerScope`.** All three readers' `OnImageAvailableListener`s (`FrameAnalyzer.imageAvailableListener`, `StillCaptureController.imageAvailableListener`/`rawImageAvailableListener`) are delivered on that same background `Looper` — closing a reader from a genuinely different thread could invalidate a buffer one of those callbacks was already mid-read on (`IllegalStateException: buffer is inaccessible`, hit in production via `HistogramData.fromLumaPlane` during a routine lens-switch/backgrounding teardown, not just final unbind). `CameraController.closeImageReaders` posts the close as a task on `backgroundHandler`'s queue instead, so it can only run before a queued callback starts or after one finishes — never during, since a `Looper` only ever runs one message at a time. `FrameAnalyzer`'s and `StillCaptureController`'s buffer-reading call sites additionally catch `IllegalStateException` narrowly (dropping just that one frame, or for the still-capture JPEG side — which has exactly one pending `Image` to wait on, not a continuous stream — failing the in-flight capture through the same path `CameraRepositoryImpl.takePhoto` already handles) as a safety net for the same class of failure that isn't necessarily eliminated by the ordering fix alone (e.g. a frame already in flight through the HAL when teardown starts).
- **The live preview is rendered by app-owned GLES (`CameraPreviewRenderer`, `ui/gl/`) instead of Camera2 writing directly into a `TextureView`'s `SurfaceTexture`.** This replaced the original `SurfaceTexture`-direct design after extensive on-device investigation traced a live-preview stretching bug to it: the app requests a preview stream size via `SurfaceTexture.setDefaultBufferSize(...)`, honored exactly on cold launch, but on some *reopens* of the same session (identical `Surface`, identical requested size) the camera HAL was confirmed (via its own debug log, Pixel 9 Pro `caiman_beta` build) to silently deliver a different actual stream size/aspect instead — no callback or public Camera2 API exposes this after the fact, so the app's own crop transform (computed once from the *requested* size) kept rendering the actually-different buffer miscalibrated. Ruled out first, in order, before landing on this fix: re-asserting the identical requested size on every resume (no effect — not a stale-request problem); awaiting `CameraDevice.StateCallback.onClosed()` before reopening the same camera ID via `deviceClosedSignal` (a real, independently-justified Camera2 hygiene fix — Google's own `Camera2Basic` sample does the same — kept regardless, but didn't fix this bug either, ruling out an async-close race); a center-fit vs. center-crop transform change (doesn't help — the distortion is baked in by an earlier non-uniform remap step in the transform math, not the final crop amount); a second-`LifecycleEventObserver` fresh-`Surface`-per-reopen attempt (the crash described above). The fix that actually works: `CameraController` targets its preview repeating request at its own `YUV_420_888` `ImageReader` (mirroring the existing still-JPEG reader — session stays a 2-output configuration, not 3, avoiding the unrelated stream-combination regression issue #6 already found once) instead of a caller-supplied `Surface` — an `ImageReader`'s dimensions are a hard, verifiable *construction-time* contract (`onConfigureFailed` if unmet, never silently substituted), unlike a `SurfaceTexture`'s requested buffer size. `CameraPreviewRenderer` owns a dedicated `HandlerThread` + EGL context/surface (against the on-screen `TextureView`'s `SurfaceTexture`) and a GLES 2.0 YUV→RGB shader pipeline; `CameraController.setPreviewFrameListener` hands each delivered `Image` to it, and its crop/rotation transform is built from that frame's *actually-delivered* `Image.width`/`height` every time, not an assumption — self-correcting on every reopen regardless of what the HAL actually did. `SENSOR_ORIENTATION` rotation, handled automatically before by the `TextureView`/`SurfaceTexture` compositor for an on-screen consumer, has to be applied explicitly by the renderer now (an `ImageReader` never gets that treatment — the same reason zebra's `analysisRotationDegrees` already needed it). Zebra classification folded into the same preview `ImageReader` frames (see below) rather than needing its own capture mechanism, a net simplification. `repackPlane`'s de-interleaving (`pixelStride != 1`, the common case for chroma planes on this device) must bulk-read each row into a reused on-heap `ByteArray` and de-interleave with a plain-array loop, not per-byte `ByteBuffer.get`/`put` calls — the latter was confirmed on-device as the dominant per-frame CPU cost, low enough preview frame rate to be visibly janky; `uploadTexture` similarly must call `glTexImage2D` only once per size (texture storage allocation) and `glTexSubImage2D` on every subsequent frame of that size, not reallocate storage every frame. `GL_UNPACK_ALIGNMENT` is set to 1 in `initGl` to match the repacked buffers' tight packing (GL's default 4-byte row alignment would misread rows whenever a plane width isn't a multiple of 4). Known residual risk, not yet fully validated: rotation/color-calibration correctness across GPU vendors other than the one Pixel 9 Pro device available to this project (rotation and color both visually confirmed correct on that device). A brief frozen-last-frame hitch during any camera reopen (background/foreground, lens switch) is expected — `CameraController` closing/reopening the `CameraCaptureSession` has inherent latency with no new frames in flight, which is a Camera2 session-teardown cost, not a rendering bug.

**UI/overlay bug history:**
- **Corner-hopping overlays clip if rotated the wrong way** (`HistogramOverlay`'s `HistogramMarks`, `LutResolvingIndicator`'s `RotatingBadge`) — a real, shipped bug: rotating a fixed-size box with a `Modifier`-level rotation only transforms how it *paints*, not what size the layout system thinks it is, so e.g. a 96x48dp box rotated 90° was still *positioned* using its unrotated 96x48dp bounds while visually occupying a 48x96dp footprint — with only a small fixed corner margin, that pushed part of it off-screen (clipped against the screen edge) once anchored near a corner in landscape. Fixed by measuring the rotated footprint directly (swapping width/height for a 90°/270° rotation) so the layout system reserves the correct post-rotation space before alignment happens, then drawing the same always-upright-logical-space content into that reserved area via a `DrawScope.rotate` around its own center, so what's drawn always fits exactly inside what's laid out.
- **Horizon-line static thirds must not rotate with the device** (`HorizonLineOverlay`) — an earlier version rotated the *whole* line (all three segments) by the device's quadrant-snapped counter-rotation so the static outer reference stayed visually horizontal through a 90° turn into landscape. That broke the property the line exists for: it's meant to sit exactly inside `ViewfinderGridOverlay`'s own thirds, and the grid applies *zero* orientation compensation (its dividers are always plain `size.width/3`/`size.height/3`, frame-relative, not gravity-relative — correct for a rule-of-thirds composition grid). Rotating the line's segments while the grid never rotates only coincidentally lined up in portrait (quadrant 0° ⇒ no rotation applied); in landscape (90°/270°) the line visibly drifted off the grid's fixed divider positions. Fix: instead of rotating a fixed X-axis layout by the quadrant angle, the line picks its *drawing axis* directly from the quadrant (X-axis thirds in portrait/upside-down, Y-axis thirds in landscape) so it lands on the grid's own fixed coordinates in every orientation by construction, with nothing left to compensate for. Only the small residual "how far off level" angle still gets a live rotation, applied to the dynamic center segment alone, pivoting around the canvas center.
- **`FocusRing` sizing** (issue #21 on-device-QA follow-up) — the manual-focus ring/loupe originally rendered at a small fixed 156dp regardless of viewfinder size. Once a later UX rework recentered the ring to the viewfinder's own middle (rather than the touch point) whenever only `FocusDial` — not the screen itself — is held, a fixed 156dp ring read as too small next to the rest of the viewfinder. It now scales to ~92% of the viewfinder's own shorter on-screen dimension (`ui/CameraScreen`'s `focusRingDiameter`), with the loupe's crop radius scaled by the same ratio so magnification doesn't turn to mush at the larger size.
- **Auto→manual exposure pin timing** (`ui/CameraScreen`'s `LaunchedEffect(uiState.manualModeEnabled)`) — manual mode's dials appear the instant `ModeToggle` is tapped, but the camera doesn't actually lock exposure (`CONTROL_AE_MODE_OFF`) until 3A has genuinely gone quiet. A fixed short delay was tried first and rejected: a small EV nudge settles in a couple of frames, but a large AE-compensation swing (e.g. toggling to manual right after dragging several stops of EV) can take much longer to converge, and the fixed wait was pinning manual mode to a reading 3A hadn't finished moving toward yet — visibly jumping brightness on the switch. Replaced with a debounce that restarts its quiet-window every time either live ISO/shutter reading changes, only proceeding once both have genuinely stopped moving, bounded by a timeout safety net in case 3A never fully quiets down (e.g. flicker).

**Open questions:**
- Manual white balance scope not yet defined (manual focus shipped in issue #21 — see above).
- **Issue #45's RAW/DNG pipeline has been confirmed on-device**: the shutter fires a combined JPEG+RAW capture, the resulting `.dng` is saved, opens from the gallery, and is recognized as RAW.
- Issue #21's tap-to-focus (region + `CONTROL_AF_MODE_AUTO` trigger, confirmed causing real lens movement on-device) and the AF-state-driven tap indicator are confirmed working via targeted on-device `CaptureResult` logging (Pixel 9 Pro). The `FocusDial` rework's own gesture wiring (drag → `CameraViewModel.setManualFocusDistance` → `CameraController`'s `pendingManualFocusDiopters`/`updatePreviewRepeating`) was confirmed firing correctly via a targeted on-device `adb`-driven drag + temporary logcat check (Pixel 9 Pro) — but not full hands-on QA. Still not verified by full manual gesture QA: `FocusDial`'s own drag-sensitivity feel (`DragPxPerFullTurn`) and one-handed-while-holding-the-screen ergonomics, the simultaneous-hold edge case (screen + dial held together, then released in either order), the ring's on-screen proportions, loupe/focus-peaking image quality at the larger magnification, and the tap indicator's timing constants (`AfScanStartGraceMs`/`FocusIndicatorHoldAfterLockMs`) — these are reasoned defaults, not device-tuned.
- **The GLES preview rewrite above has been confirmed correct on-device (Pixel 9 Pro, `caiman_beta`)**: cold launch, repeated background/foreground and lens-switch cycles, gallery round-trip, physical device rotation, zebra overlay in both auto and manual mode, and normal still capture all render correctly with no crashes and no stretching. Frame rate was initially visibly low after the rewrite (see key-decisions entry above — CPU repack cost) and confirmed fixed on-device after the bulk-array/`glTexSubImage2D` change. Still open: no leaked `HandlerThread`/EGL context confirmed yet across many rapid reopens (Memory Profiler check not yet done); only tested against this one Pixel 9 Pro device — a second device with a different GPU vendor would meaningfully de-risk the YUV plane stride/`pixelStride` handling for other hardware.
