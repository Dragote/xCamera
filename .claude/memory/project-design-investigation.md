The user is unhappy with how xCamera's skeuomorphic camera-body chrome (dials, levers, shutter button — see [[project-vision]]/[[camera-feasibility-android]]) looks — "cheap" — compared to the design references they have on hand. Two isolated fixes were tried and both rejected on-device as of 2026-08-14:

1. **Color/palette alone** — user pre-emptively ruled this out before any code was written: even repainting the body beige and giving each control its own color would still feel cheap. (There's also a prior, separate abandoned attempt at this: git branch `experiment/amber-drum-dial-redesign`, never merged, which repainted the whole body flat amber and dropped grain texture + the mechanical seal/unseal transition — likely why *that* didn't land either.)
2. **Rendering technique alone, color held constant** — built and shipped a pilot (`DialWheel.kt`'s `drawWell`/`drawBarrel`): replaced hard-edged banded gradients/inset-shadow tricks with a real cached soft-blur "blob" primitive (new `SoftBlob.kt`, alpha-only box blur, mirrors `CameraChrome.kt`'s existing `grainBrush` bake-once-and-cache pattern) for contact shadows, rim highlights, and a specular highlight on the barrel. Compiled clean, tested on a connected device — user's verdict: barely any visible difference, and the design needs reworking from scratch. **Reverted** — `git checkout`'d `DialWheel.kt`, deleted `SoftBlob.kt`, working tree is clean.

**Why:** established via direct back-and-forth diagnosis this session — comparing `CameraChrome.kt`/`AppChrome.kt` (deliberately dark/near-monochrome "matte black plastic" body, single global `Accent` reused by every dial) against real reference screenshots (light warm taupe body, each control its own saturated candy-plastic hue: blue/orange fluted knobs, purple shutter, green focus ring) suggested two separate hypotheses — wrong palette architecture, and hand-drawn-banded vs. true-soft rendering technique. Neither hypothesis alone, tested independently, closed the gap when actually viewed on-device. This means the "cheap" feeling isn't reducible to either single axis — it may need both changed together, or may need a different technical approach entirely (baked/pre-rendered image assets instead of procedural Canvas drawing — discussed but not attempted, since generating such assets needs an external tool/pipeline, not something doable purely in-repo).

**Neo-skeuomorphic direction (2026-08-18) — abandoned, and its code no longer exists:** the pause above held until 2026-08-18, when the user brought the redesign back themselves — not via either previously-falsified axis (color-only / technique-only on the existing dark "matte black plastic" body), but a wholesale new visual language: neo-skeuomorphic, dark sage-green (`#2F5245` body / `#24443A` recessed sockets / mint-green `#BCE3BF`→`#8CC79E` raised surfaces), authored in a claude.ai/design project (a neo-skeuomorphic round-button study, project id `618ba008-855c-4ae5-92df-6597938e738d`, read via the `DesignSync` MCP tool) and iterated outside the repo (Downloads folder) before being brought in. User's stated intent: to rewrite the app's whole design system, not just camera chrome.

First concrete step taken: ported 4 components 1:1 from that design project into `feature/camera/ui/component/` — `NeoDialWheel.kt`, `NeoDialWheelVertical.kt`, `NeoSkeuoButton.kt`, `NeoSkeuoToggle.kt` — each with an `@Preview`. Fixed one real bug in transit (`NeoSkeuoButton`'s `rp` referenced `r` before its declaration — didn't compile in the source `.kt`). Deliberately **left as literal duplicates** rather than extracted per the project's usual "second occurrence → extract" rule: `NeoDialWheel`/`NeoDialWheelVertical` are near-total copies (axis swapped), and `lip()`/two-layer green `shadow()`/the sweep-gradient edge recur across all four — user explicitly said to just duplicate them for now when asked how to integrate. Don't extract shared helpers among these four until the user asks.

**Outcome (verified 2026-08-31 against the repo):** none of `NeoDialWheel.kt`, `NeoDialWheelVertical.kt`, `NeoSkeuoButton.kt`, `NeoSkeuoToggle.kt` appear in any of the repo's 125 commits on any ref — they only ever existed in the old machine's working tree and were lost in the machine migration. The sage-green neo-skeuomorphic direction never shipped. What shipped instead was issue #49, a wholly different identity: **"minimal chrome"** — flat OP-1-Field-style line-art, thin strokes and flat black-or-white fills on a warm-white body, no gradients/shadows/blur/grain, with a `Palette.Normal`/`Palette.Inverted` switch. #49 was an in-place rewrite: it deleted `AppChrome`/`LeverSwitch` and gutted `DialWheel`'s skeuomorphic drawing rather than preserving the old implementation alongside. Treat everything below about the Neo components as historical background only.

**Naming collision found and deliberately avoided:** the project already has a *different*, deeply production-integrated `feature/camera/ui/component/dial/DialWheel.kt` — a click-detent barrel selector (haptic ticks on each step, label/value text, mechanical open/close "shutter" animation keyed to `closedFraction`, deck-gradient integration, shared internals reused by `IsoDial`/`ShutterSpeedDial`/`LutDial`/`ExposureDial`). It shares only a name and a vague "rotary wheel" concept with the new neo-skeuomorphic design — completely different gesture model (continuous 1:1 drag, no detents). The new components were named `NeoDialWheel`/`NeoDialWheelVertical` specifically to not collide with or replace it. **The new components are not wired into any real camera screen** — pure visual reference for now, and per the user's instruction to stop there for now, don't proactively build the actual `Control Panel.dc.html` composite layout or start replacing production dials until asked. When the user does bring this forward again, the open question they'll need to resolve is how (or whether) to reconcile the new continuous-rotation visual with the existing click-detent interaction model/label text/haptics/open-close animation that the real camera screens depend on — that reconciliation work hasn't started.

**`LensDial` no longer applies here (as of 2026-08-19, one day after this memory was written):** it was swapped from `DialWheel`'s rotating-barrel click-wheel to `shared:designsystem`'s new `SteppedToggle` (straight N-detent track — lens count is small/fixed-position, unlike ISO/SHUTTER's much larger ranges that still suit a wheel). As of 2026-08-31 `DialWheel`'s production consumers are `IsoDial`, `ShutterSpeedDial`, `LutDial`, and `ExposureDial`. `FocusDial` is **not** one of them (it has its own continuous-drag gesture), and `LensDial` now wraps `shared:designsystem`'s `SteppedToggle` — don't cite either as a `DialWheel` consumer, and don't reuse stale reference material that still shows lens selection as a `DialWheel`.
